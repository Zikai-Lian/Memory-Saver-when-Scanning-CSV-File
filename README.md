# Out-of-Core CSV Aggregation Benchmark

A resource-optimization project comparing four ways to aggregate a large CSV
file in Python: naive full-load pandas, chunked pandas, Polars' lazy/streaming
engine, and DuckDB's embedded SQL engine. The goal is to show, with real
measured numbers, how much peak memory and wall-clock time you can save by
changing *how* you read data rather than what hardware you run it on.

## The problem

`pandas.read_csv(path)` is the default way most people load tabular data in
Python, but it materializes the entire file as an in-memory DataFrame before
you can do anything with it. For a file that's small relative to available
RAM this is fine. Once the file gets large -- or you're running on a memory
constrained machine (a laptop, a small cloud instance, a shared research
server) -- this becomes the actual bottleneck, causing slowdowns, swapping, or
outright OOM kills, even though the *aggregation* you actually want (a
group-by sum, a rolling average) never needs the whole file resident in
memory at once.

This project builds the same aggregation query four different ways and
measures the resource tradeoffs directly, instead of asserting them.

## Dataset

A synthetic e-commerce transactions CSV, generated by `generate_data.py`:

- **15,000,000 rows / ~876 MB** on disk
- Columns: `order_id, user_id, product_id, category, price, quantity, country, timestamp`
- Generated in 1M-row chunks with vectorized NumPy calls so that *generating*
  the benchmark data doesn't itself require loading it all into memory

The benchmark query computes, in a single pass: total revenue and order count
per `category`, and average order value per `country` -- a realistic
group-by-aggregate workload that can't be answered from metadata alone; every
row has to be touched.

## The four approaches

| Approach | File | Idea |
|---|---|---|
| `naive_pandas` | `approaches/naive_pandas.py` | `pd.read_csv()` loads the whole file into one DataFrame, then `.groupby()` |
| `chunked_pandas` | `approaches/chunked_pandas.py` | `pd.read_csv(chunksize=...)` iterates fixed-size chunks, aggregating and merging partial results as it goes |
| `polars_lazy_streaming` | `approaches/polars_lazy.py` | `pl.scan_csv()` builds a lazy query plan; Polars' streaming engine executes it in batches under the hood |
| `duckdb_sql` | `approaches/duckdb_approach.py` | DuckDB queries the CSV directly with SQL; the engine handles buffering/spilling internally |

All four compute the exact same aggregation and are checked against each
other for correctness (see below) -- this isn't four different analyses, it's
one analysis done four different ways.

## Methodology

Each approach runs as its **own fresh subprocess** (`measure_run.py`), so
memory measurements can't leak between runs. Peak memory is read from
`resource.getrusage(RUSAGE_CHILDREN).ru_maxrss` immediately after that one
child process exits -- this is the kernel-reported peak RSS for that process's
entire lifetime, not a sampled/polled approximation. Wall-clock time is
measured around the subprocess call with `time.perf_counter()`.

`benchmark.py` runs all four approaches in sequence, parses each one's result,
and confirms every non-reference approach's output **exactly matches** the
first (reference) approach's output before recording it -- an optimization
that silently produces the wrong number is worse than no optimization, so
correctness is checked automatically on every run, not just eyeballed once.

Run it yourself:

```bash
pip install pandas polars duckdb matplotlib numpy
python3 generate_data.py --rows 15000000 --out data/transactions.csv
python3 benchmark.py --input data/transactions.csv
python3 plot_results.py
```

## Results

Measured on a 2-vCPU / 7.8 GB RAM container, 876 MB / 15M-row input:

| Approach | Peak RSS | Wall time | vs. naive (memory) | vs. naive (speed) |
|---|---:|---:|---:|---:|
| `naive_pandas` (load-all) | 3,048 MB | 15.0 s | baseline | baseline |
| `chunked_pandas` | 273 MB | 14.4 s | **11.1x less** | ~same |
| `polars_lazy_streaming` | 972 MB | 3.0 s | 3.1x less | **5.0x faster** |
| `duckdb_sql` | 246 MB | 4.9 s | **12.4x less** | 3.1x faster |

All four approaches returned **identical** aggregation results (total
revenue, order counts, per-category and per-country breakdowns) --
correctness was not sacrificed for any of the resource savings.

## Analysis / tradeoffs

**Naive pandas** is simplest to write and is fine until the file approaches
or exceeds available RAM -- at which point it's the first thing that breaks,
usually in production, usually at the worst time. It's included here as the
baseline everyone starts from.

**Chunked pandas** cuts peak memory by over 11x with almost no speed penalty,
using nothing beyond the standard library and pandas itself -- no new
dependencies. The cost is code complexity: you're manually managing partial
aggregation state (`category_sum`, `category_count`, etc.) and combining it
correctly, which is exactly the kind of bookkeeping that's easy to get subtly
wrong (this is why the correctness check across all four approaches matters
-- it would have caught a bug here).

**Polars' streaming engine** gets the best speed in the benchmark (5x faster
than naive) with a solid memory reduction too, because its lazy query
planner can push filters/projections down and only stream what's needed
through each operation, all while using a genuinely parallel, Rust-based
execution engine instead of pandas' single-threaded one. The API is also
close to pandas' in spirit but requires learning Polars' expression syntax.

**DuckDB** gets the best memory result in the benchmark (12.4x less than
naive) and is fast, while letting the aggregation be expressed as plain SQL
against the CSV directly -- no manual chunking logic at all. This is the
strongest "resource-optimization for free" result here: you get both the
biggest memory win and a large speed win just by picking a different tool for
the same query, with arguably the simplest code of the four.

**Takeaway:** for a group-by-aggregate workload over a file that doesn't
comfortably fit in memory, both Polars and DuckDB beat naive pandas on both
memory *and* speed simultaneously -- there's no real tradeoff to accept here,
just a better default choice of tool. Chunked pandas remains a useful
fallback when you can't add a new dependency but still need to bound memory.

├── measure_run.py            # isolated subprocess wall-time + peak-RSS measurement
├── benchmark.py               # runs all approaches, checks correctness, writes CSV
├── plot_results.py            # renders the comparison chart
├── approaches/
│   ├── naive_pandas.py
│   ├── chunked_pandas.py

    └── transactions.csv       # generated, not checked in (see .gitignore)

## Possible extensions

- Sweep the dataset size (1x, 5x, 10x RAM) to show where naive pandas'
  curve actually breaks vs. where the others stay flat
- Add a fifth approach using `pyarrow.csv` + `pyarrow.compute` for another
  reference point
- Push the aggregation into a real Postgres/ClickHouse instance and compare
  against embedded-engine (DuckDB) numbers
- Wrap the winning approach (DuckDB) in a small FastAPI service that accepts
  a file path and query parameters and returns the aggregation as JSON
